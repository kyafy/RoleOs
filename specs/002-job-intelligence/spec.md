# 功能规格：Job Intelligence（岗位智能）

**功能分支**：`002-job-intelligence`  
**创建日期**：2026-09-19  
**状态**：可进入规划  
**输入依据**：`docs/RoleOS-7-Feature-Specs-Revised/002-job-intelligence-revised.md`

## 用户场景与测试

### 用户故事 1 - 发现并保存真实岗位（优先级：P1）

作为已经建立职业档案的求职者，我希望按关键词、城市及基础偏好从 Boss 直聘获取真实岗位，以便后续筛选与决策基于可追溯的岗位事实。

**优先级原因**：真实且稳定的岗位事实是全部岗位分析、匹配和投递流程的入口。

**独立测试**：在用户可见且已登录的招聘网站会话中执行一次低频搜索，系统取得岗位列表及详情，保存原始信息并形成统一岗位记录；字段缺失时明确标记未知。

**验收场景**：

1. **假设** 用户已拥有职业档案和可用的招聘网站会话，**当** 其按关键词与城市发起搜索，**那么** 系统获取至少一批真实岗位列表和详情，记录来源、外部岗位标识、来源链接及原始信息。
2. **假设** 原始岗位字段完整，**当** 系统完成标准化，**那么** 统一岗位记录包含标题、公司、城市、薪资、经验、学历、职位描述、发布时间和招聘方活跃度。
3. **假设** 薪资、经验、学历或发布时间缺失，**当** 系统标准化该岗位，**那么** 对应字段为未知而不是推断值。
4. **假设** 同一来源岗位的职位描述发生变化，**当** 系统再次获取该岗位，**那么** 更新当前岗位快照，并保留可识别的更新时间和内容摘要变化。

---

### 用户故事 2 - 去重并执行确定性硬过滤（优先级：P1）

作为求职者，我希望系统自动合并重复岗位，并按城市、薪资、经验和目标职业方向排除明显不合适的岗位，以减少无效分析成本。

**优先级原因**：去重和硬过滤是控制 Broad Apply 成本、避免重复决策的必要条件。

**独立测试**：输入含强标识重复、内容重复、明确冲突及字段缺失的 20 个岗位；系统只保留唯一岗位，并分别输出通过、拒绝或未知及逐项原因。

**验收场景**：

1. **假设** 两条岗位的来源与外部岗位标识相同，**当** 它们进入候选池，**那么** 只形成一个岗位和一个用户候选关系。
2. **假设** 两条岗位的外部标识不同，但公司、标题、城市及职位描述内容摘要一致，**当** 它们进入候选池，**那么** 系统将其识别为重复岗位。
3. **假设** 岗位城市、最低薪资、经验门槛或职业方向与用户偏好存在明确硬冲突，**当** 执行硬过滤，**那么** 结果为拒绝并给出具体规则原因。
4. **假设** 某个硬过滤所需字段缺失或表述无法可靠判断，**当** 执行硬过滤，**那么** 结果为未知，岗位仍可进入轻量分析。

---

### 用户故事 3 - 查看可解释的 Broad Ranking（优先级：P1）

作为求职者，我希望通过低成本的轻量分析查看候选岗位排序、推荐和风险说明，以便优先审阅最值得 Broad Apply 的岗位。

**优先级原因**：可解释排序直接把原始岗位池转化为用户可行动的优先列表，也是本 Feature 的核心价值。

**独立测试**：对一批通过或未知硬过滤的岗位执行轻量分析，用户能看到总分、策略建议、原因、重要信号和警告；招聘方活跃度只产生弱影响。

**验收场景**：

1. **假设** 岗位通过硬过滤，**当** 轻量分析完成，**那么** 候选结果同时包含规则信号、结构化语义判断、排序分、策略建议、解释、重要信号及警告。
2. **假设** 两个岗位其他条件相近但招聘方活跃度不同，**当** 计算排序，**那么** 活跃度可以影响先后次序。
3. **假设** 不活跃岗位在技术方向和职业目标上明显更匹配，**当** 与活跃但相关性较低的岗位比较，**那么** 活跃度不得压过核心匹配信号。
4. **假设** 语义判断暂时失败，**当** 用户查看候选池，**那么** 岗位、硬过滤和已有规则信号仍被保留，并明确显示分析待处理或失败状态。

---

### 用户故事 4 - 由用户决定 Broad、Targeted 或 Skip（优先级：P1）

作为求职者，我希望系统推荐高价值岗位升级为 Targeted Apply，但由我最终决定升级、保留 Broad 或跳过，以便深度链路只投入到我确认的岗位。

**优先级原因**：人工决策是防止系统擅自扩大成本或改变求职策略的核心控制点。

**独立测试**：对一个被推荐升级的 Broad Candidate，验证推荐不会自动改变策略；用户分别执行升级、保留或跳过后，系统保存其选择及理由，重复请求不产生额外状态变化。

**验收场景**：

1. **假设** 一个 Broad Candidate 被评为高价值，**当** 系统生成升级建议，**那么** 当前策略保持 Broad，直到用户确认。
2. **假设** 用户确认升级，**当** 决策被接受，**那么** 该用户候选关系变为 Targeted Apply，Canonical Job 本身不被修改。
3. **假设** 用户选择保留 Broad 或 Skip，**当** 决策被接受，**那么** 系统尊重用户选择并保存决策理由。
4. **假设** 同一决策被重复提交，**当** 系统处理请求，**那么** 不产生重复推进或冲突记录，并返回当前有效状态。

---

### 用户故事 5 - 在 Job Pool 管理岗位并安全恢复抓取（优先级：P2）

作为求职者，我希望在网页中浏览候选池、查看岗位详情并处理策略；当首选浏览能力失败或出现人工验证时，系统可以安全恢复或暂停，而不会丢失已有岗位和流程状态。

**优先级原因**：可观察的用户界面和安全恢复能力使真实岗位链路可用、可控、可验收。

**独立测试**：用户可从候选列表进入详情、筛选状态并执行核心决策；模拟首选浏览能力可恢复失败后从已保存业务状态切换备用能力；模拟验证码后流程暂停并可由用户处理后恢复。

**验收场景**：

1. **假设** 候选池已有岗位，**当** 用户浏览列表或详情，**那么** 可查看岗位事实、原始与标准化职位描述、过滤结果、排序解释、当前策略、来源和抓取状态。
2. **假设** 用户按 Broad、Targeted、Skipped、Pass 或 Unknown 筛选，**当** 筛选生效，**那么** 列表只显示符合条件的候选岗位。
3. **假设** 首选浏览能力发生可恢复失败，**当** 系统选择备用能力，**那么** 从持久化的搜索业务状态重新导航和抓取，不复用旧能力的页面引用、会话或内部句柄。
4. **假设** 页面出现验证码、人工验证、平台风险提示或敏感确认，**当** 系统识别该状态，**那么** 立即暂停给用户，不尝试绕过，并在用户处理后从业务步骤恢复。
5. **假设** 页面结构变化导致本次抓取失败，**当** 用户查看系统，**那么** 已保存岗位和核心流程状态保持可用，失败原因与可重试状态清晰可见。

### 边界情况

- 同一岗位重复出现且新快照内容改变时，更新岗位事实，不重复创建用户候选关系，也不覆盖用户已有策略决定。
- 多城市或远程岗位按页面明确事实评估；没有明确事实时使用未知，不根据标题猜测。
- 薪资区间、薪资月数或经验表达模糊时，无法可靠比较的规则结果必须为未知。
- 语义分析返回缺字段、非法分值或无法验证的结构时，不得持久化为有效排序结果；既有确定性结果仍保留。
- 用户已 Skip 的岗位再次被抓取时，不得自动恢复为 Broad 或 Targeted。
- 浏览能力切换时，不迁移页面引用、Cookie、标签页或会话；只能使用持久化业务状态重新开始当前业务步骤。
- 招聘网站不可达、用户未登录或会话失效时，搜索失败必须可解释且可重试，不得丢失此前岗位。
- 不得通过自动解验证码、隐藏式登录或保存招聘网站密码完成岗位抓取。

## 需求

### 功能需求

- **FR-001**：系统必须允许已建立职业档案的用户使用关键词、城市及基础偏好发起低频岗位搜索。
- **FR-002**：V1 必须以 Boss 直聘作为首个真实岗位来源，并获取岗位列表及岗位详情。
- **FR-003**：系统必须在用户可见、可停止且由用户自行完成登录的招聘网站会话中执行抓取，不得保存招聘网站密码。
- **FR-004**：系统必须将来源岗位信息转换为统一岗位事实，并保留原始来源数据以支持追溯和重新解析。
- **FR-005**：统一岗位事实至少包含用户归属、来源、外部岗位标识、标题、公司、城市、薪资、经验要求、学历要求、原始与标准化职位描述、发布时间、招聘方活跃度、来源链接、来源状态、内容摘要及附加信息。
- **FR-006**：任何缺失或无法可靠解析的来源字段必须表示为未知，不得推断或虚构。
- **FR-007**：Canonical Job 必须只表示外部岗位事实；过滤、排序、策略及用户决策必须保存在独立的用户候选关系中。
- **FR-008**：系统必须首先按“来源 + 外部岗位标识”去重，再按“标准化公司 + 标准化标题 + 城市 + 职位描述内容摘要”识别内容重复。
- **FR-009**：重复岗位不得重复进入同一用户的 Job Pool 或 Ranking；再次获取的事实变化必须更新当前快照并记录更新时间和摘要变化。
- **FR-010**：系统必须使用确定性规则评估城市、薪资、经验及目标职业方向，输出 Pass、Reject 或 Unknown 及逐项原因。
- **FR-011**：Unknown 不得等同于匹配或拒绝，并允许进入后续轻量分析。
- **FR-012**：被明确 Reject 的岗位不得进入 Broad Ranking，但必须保留可解释的过滤记录供用户查看。
- **FR-013**：Broad Apply 必须只执行轻量职位分析、轻量匹配和排序，不得自动进入经历深挖、项目升级、深度 Gap 分析或岗位定制简历。
- **FR-014**：岗位排序必须组合确定性规则信号与结构化语义判断；语义判断结果在保存前必须通过结构校验。
- **FR-015**：每个已排序候选至少包含排序分、策略建议、解释、重要信号、警告和语义分析状态。
- **FR-016**：招聘方活跃度只能作为弱信号，不得压过职业方向、技术相关性、薪资和职业目标等核心信号。
- **FR-017**：语义判断失败时，系统必须保留岗位、过滤结果和规则信号，并将分析标记为 Pending 或 Failed 以便重试。
- **FR-018**：系统可以推荐将候选升级为 Targeted Apply，但不得自动改变用户当前策略。
- **FR-019**：用户必须能够确认 Promote to Targeted、Keep Broad 或 Skip；系统必须保存当前策略、推荐、用户决定、理由与时间。
- **FR-020**：用户决策必须幂等；重复或不兼容决策不得造成额外状态推进或篡改 Canonical Job。
- **FR-021**：系统必须提供 Job Pool 页面，显示列表、详情、过滤状态、排序分与解释、当前策略、来源、活跃度、发布时间和抓取状态。
- **FR-022**：用户必须能够按 Broad、Targeted、Skipped、Pass 和 Unknown 筛选候选池，并能刷新、打开来源岗位及执行策略决策。
- **FR-023**：岗位详情必须同时展示原始与标准化职位描述、硬过滤结果、排序信号和解释、当前策略及来源链接。
- **FR-024**：岗位业务只能通过招聘网站能力边界使用浏览能力；职业领域不得依赖具体浏览产品、页面选择器或内部句柄。
- **FR-025**：系统必须支持首选浏览能力、备用浏览能力及用户手动指定能力，并记录每次抓取实际使用的能力和结果。
- **FR-026**：首选浏览能力发生可恢复失败时，系统可以选择备用能力，但必须从持久化搜索业务状态重新导航、重新抓取并恢复业务步骤。
- **FR-027**：浏览能力切换不得迁移或复用 ElementRef、页面快照、标签页、Cookie、会话或其他提供方内部状态。
- **FR-028**：识别到验证码、人工验证、平台风险警告或敏感确认时，系统必须进入 Paused for Human，保存等待原因和恢复位置，且不得自动绕过。
- **FR-029**：页面变化、来源不可达或浏览失败不得破坏已保存岗位与用户决策；失败必须具备可观察状态、原因和受控重试入口。
- **FR-030**：普通日志和用户界面不得暴露招聘网站凭据、完整 Cookie、会话令牌或不必要的个人职业敏感信息。

### 关键实体

- **岗位（Job）**：从外部来源标准化而来的岗位事实，保存原始与标准化内容、来源身份、当前快照和内容摘要，不承载用户求职策略。
- **岗位候选（Job Candidate）**：某个用户与岗位之间的候选关系，保存硬过滤结果、排序结果、当前策略、推荐、语义分析状态及元数据。
- **岗位决策（Job Decision）**：用户对候选岗位作出的 Promote、Keep Broad 或 Skip 决定，包含理由、时间及幂等标识。
- **岗位搜索（Job Search）**：一次可恢复的搜索请求，记录查询条件、业务步骤、实际浏览能力、抓取状态、失败或人工等待原因。
- **过滤评估（Filter Evaluation）**：城市、薪资、经验和目标职业方向等确定性规则的逐项结果、原因及汇总状态。
- **排序评估（Ranking Evaluation）**：规则信号与结构化语义信号的可解释组合，包含分数、推荐、原因、重要信号、警告和分析状态。
- **来源快照（Source Snapshot）**：岗位原始来源数据及采集时间、来源状态与内容摘要，用于追溯和解析调整后的重放。

## 成功标准

### 可衡量结果

- **SC-001**：在一次真实、低频的 Boss 直聘搜索验收中，用户能在 5 分钟内从发起搜索到看到至少 1 个包含列表与详情数据的 Canonical Job，且 100% 岗位可追溯到来源链接和原始快照。
- **SC-002**：对含强标识重复和内容重复的测试集，100% 已知重复岗位不会重复进入同一用户的候选池；更新后的岗位仍保持原有用户策略。
- **SC-003**：对至少 20 个覆盖匹配、明确冲突和字段缺失的岗位样本，城市、薪资、经验与目标职业方向规则均输出 Pass、Reject 或 Unknown 及原因，缺失数据被误判为匹配的比例为 0%。
- **SC-004**：对所有进入 Broad Ranking 的岗位，100% 可展示分数、策略建议、解释、重要信号和警告；单独提高招聘方活跃度不能使明显低相关岗位越过明显高相关岗位。
- **SC-005**：系统推荐升级的岗位在用户确认前自动变为 Targeted 的比例为 0%；用户完成 Promote、Keep Broad 或 Skip 后，界面中的有效策略在 2 秒内一致更新。
- **SC-006**：模拟一次首选浏览能力可恢复失败后，备用能力能够从已保存业务步骤继续并完成搜索，跨能力复用页面引用或会话的次数为 0。
- **SC-007**：在验证码或人工验证验收中，100% 对应搜索进入人工暂停且不尝试绕过；用户处理后可以从记录的业务步骤继续。
- **SC-008**：在语义判断、页面解析或来源访问失败的验收中，已保存岗位和用户决策丢失率为 0%，用户能看到失败原因和允许的后续动作。
- **SC-009**：用户可不依赖开发人员完成 Job Pool 浏览、详情查看、状态筛选、来源打开以及 Broad/Targeted/Skip 决策五类核心操作。

## 假设

- V1 以单用户、低频、用户主动触发的真实求职场景为目标，不承诺无人值守批量抓取或规模化采集。
- 用户负责在自己可见的浏览会话中完成 Boss 直聘登录，并遵守平台条款、频率限制及人工验证要求。
- 002 只为 Targeted Apply 建立推荐和用户确认入口；确认后的深度 JD 分析、经历匹配、Gap、经历深挖、项目升级和岗位定制简历由后续 Feature 实现。
- 语义判断用于轻量岗位质量和相关性判断，不替代确定性硬过滤，也不能直接改变用户策略或长期流程状态。
- V1 的内容去重以确定性规范化与内容摘要为准，不使用 Embedding 或复杂机器学习去重。
- 招聘网站页面可能变化，因此原始快照、失败状态和可恢复业务步骤是验收范围；绕过平台安全控制不在范围内。

## 范围边界

本 Feature 不包含多招聘网站聚合、无人值守批量投递、验证码绕过、完整深度 Requirement Analysis、Experience Match、Gap Analysis、Experience Mining、Project Upgrade、Claim-Evidence、Resume Compiler、正式投递、Outcome Feedback、Embedding 去重、复杂机器学习 Ranking、多智能体编排或通用 Workflow Engine。
