# RoleOS 阶段性 Feature 自动推进

## Feature 定义与边界

Feature 是一份已明确的阶段性功能实现文档。

它定义：

- 要实现的业务闭环；
- 包含和不包含的内容；
- 关键规则、实现约束和验收标准；
- 已确定的模块、数据、接口和测试要求。

Feature 的范围以文档为准：

- 必须完整实现文档中的闭环与验收项；
- 不得擅自缩小范围；
- 不得增加文档外的功能。

User Story、Plan 和 Tasks 只负责拆分执行，不改变 Feature 范围。

复杂度只影响任务拆分和测试深度，不影响交付范围。

文档未明确的实现细节可采用最小方案；涉及新增公共概念、依赖、数据表、接口或安全边界时，必须询问用户。

## 输入与恢复

- 输入必须是阶段性 Feature 实现文档路径、由该文档生成的 `specs/.../spec.md` 路径，或“继续当前 Feature”。
- 新 Feature：以该实现文档为第一交付依据，并用需求文档、技术方案、AI 编程指南和项目宪法校验其一致性；已有 Feature：读取 `.specify/feature.json` 和该目录的 `tasks.md`，从首个 `[ ]` 任务恢复。
- 不得并行推进两个 Feature。若当前 Feature 与输入不一致，先报告可选的切换或新建动作。

## 开工检查

1. 完整阅读阶段性 Feature 实现文档、`.specify/memory/constitution.md`、`AGENTS.md` 与本 Feature 已有产物。
2. 读取 `docs/RoleOS需求文档.md`、`docs/RoleOS技术方案.md`、`docs/RoleOS_AI编程指南.md` 的相关章节，只用于校验上位约束，不得以此扩大该 Feature。
3. 检查 `.specify/extensions.yml`，按各 Spec Kit Skill 的 Hook 规则执行。
4. 校验前序 Feature 的公开契约或迁移是否存在；缺失时停止，说明必须先完成的 Feature，不得自造替代物。

## 自动工作流

按缺失产物依次调用并完成：

```text
specify → clarify → plan → tasks → analyze → implement → converge → 验收
```

- 先判定复杂度：仅限单模块、无数据模型/契约/外部副作用、预计不超过 3 个独立任务的阶段文档可使用“轻量模式”（明确任务契约 → 实现 → 验证）；其余均使用完整流程。复杂度只影响流程深度，不得扩大 Feature 范围。
- `clarify` 不是固定步骤：仅当 Spec 中仍有影响范围、安全、数据归属、人工审批、外部副作用或关键体验的未决问题时运行。能由事实来源确定的内容必须写入假设，不能把普通实现选择抛给用户。
- `plan` 必须通过宪法检查；新增依赖、模块、工作流类型或跨越三项核心能力时视为软门禁。
- `tasks` 必须按用户故事组织，包含测试、迁移、契约和验收任务；若 Spec 有验收场景、示例输入输出、错误案例或性能指标，必须映射为具体测试任务和最终验收项；不设置“Tasks 后固定停点”。
- `analyze` 发现矛盾时先修正文档；若需要改变已批准边界，进入软门禁。
- `implement` 按 Phase 执行，任务级运行相关测试，只有验证通过才能勾选 `[X]`。每完成一项立即选择下一个依赖已满足的未完成任务并继续；普通构建/格式/缓存问题必须自行修复和重试。
- `converge` 对照 Spec、Plan、Tasks 与代码，把遗漏的实现补回任务清单；所有任务完成后才进入验收。

## 连续执行与恢复协议

本 Skill 的“自动推进”是一个持久目标，不是一串等待用户逐条发送的独立命令。调用本 Skill 即表示用户明确要求连续推进当前 Feature；若运行环境提供 Goal/长时任务能力，必须在确认 Feature 路径和停止条件后建立或复用一个持久 Goal，并仅在 Feature 验收完成时标记完成。Phase 完成、单次 `implement` 返回或一次 turn 结束都不是 Goal 完成条件。

生成 `tasks.md` 后，按以下控制循环推进：

1. 从 `tasks.md` 找到首个含未完成任务且依赖已满足的 Phase；没有则进入 `converge` 和验收。
2. 主动执行一次 `speckit-implement`，本次范围限定为该 Phase；Phase 内逐 Task 实现、验证并勾选。
3. Phase 验证通过后写 `commentary` 检查点，立即重新读取 `tasks.md`，选择下一 Phase 并再次执行 `speckit-implement`。
4. 若运行时在检查点后结束了当前 turn，下一次 Goal continuation 必须执行同一恢复算法，不依赖上一条回复文本，也不重做已验证任务。
5. 只有 Feature 全部验收、软门禁、明确暂停三类条件可以退出控制循环。

`tasks.md` 的勾选状态和验证证据是进度真相；不得把模型回复中的“完成”“Phase done”或 `completed` 字样当成实现成功。每次恢复都要重新检查任务、代码和测试证据。

若运行环境没有 Goal/长时任务能力，Skill 本身不能在发送 final 后自行唤醒。此时必须明确告知用户需要宿主调度；事件监听、轮询降级、幂等恢复和机器可读检查点协议见 [执行编排](references/execution-orchestration.md)。没有 Goal 或宿主调度器时，不得声称可在 final 后自动继续。

## 多层文档门禁

按从上到下的优先级校验，任一层与下层冲突时以上层为准：

1. **宪法门禁**：真实性、人工控制、Workflow/Agent 隔离、领域边界和最小复杂度；违反即停止。
2. **Feature 文档门禁**：阶段性实现文档的包含/排除项、已定实现路径、模块落位、数据/接口名称、测试守点与验收标准；任务不得发明未定义的产品能力。
3. **上位事实来源门禁**：需求、技术方案与 AI 编程指南只约束领域边界、既有契约和 V1 排除项；若与 Feature 文档冲突，停止并报告，不得擅自扩大或缩小。
4. **Spec 门禁**：每项实现必须能映射到阶段文档中的交付物，或至少一个 FR、用户故事、验收场景或明确的非功能约束；无法映射的代码、表、路径、配置或依赖不得新增。
5. **Plan 门禁**：实现前核对模块落位、数据模型、Port/Adapter、状态机和安全决策；偏离 Plan 必须先回写 Plan 或触发软门禁。
6. **Task 门禁**：逐任务执行，测试先行或与实现同批交付；只有代码、测试、检查均通过才勾选 `[X]`。
7. **验收门禁**：用阶段文档与 Spec 的验收场景、边界情况和示例作为最终判卷；通过构建不等于功能验收通过。

每次发现偏移时，先定位“宪法/事实来源/Spec/Plan/Task”中冲突的段落和任务 ID；能够回到已批准文档的，修实现或任务；需要扩展边界的，触发软门禁，不得静默漂移。

## 硬门禁

下列条件未满足不得宣布完成：

- 真实性、事实来源、人工审批与 Workflow/Agent 隔离符合宪法；
- 每个已勾选任务有实现与对应验证；
- Maven 测试和适用质量门禁通过；
- 迁移、API 契约、Adapter Contract、Workflow Recovery 与 Golden Scenario 按风险提供证据；
- 不自动 commit、push、提交申请、发送消息或执行其他外部副作用。

## 测试与全量验收

- 从 Spec 自动提取验收场景、边界情况、示例输入输出、性能目标和安全约束；每条必须映射到单元、契约、集成、恢复或端到端测试中的至少一种。没有示例时，不虚构业务数据，使用最小真实语义 Fixture。
- 对 Agent/Adapter 使用固定 Fixture 和结构化契约；不得以自由文本逐字匹配替代业务断言。
- 所有任务勾选后，必须运行一次全量验收：全量 Maven 质量门禁、相关集成/端到端测试、Spec 验收场景逐条核对、数据迁移验证、接口契约验证和敏感信息检查。
- 最终在 Feature 目录生成 `acceptance-report.md`，格式见 [验收报告模板](references/acceptance-report.md)。报告只记录事实证据；未通过或待人工验证的项目必须显式保留。

## 软门禁与提问

仅在以下情况暂停并向用户提问：

1. 需求、范围或验收标准与事实来源冲突，且无合理默认值；
2. 需要新增计划未列明的公共类型、表、配置键、REST 路径、第三方依赖或模块；
3. 需要改变宪法、数据保留/删除策略、安全策略、权限、密钥、费用或外部副作用；
4. 无法判断某个动作是否已经产生外部效果。

提问必须包含：冲突证据、2–3 个选项、每项影响、推荐项，以及恢复任务 ID。用户回答后从该任务继续，不重做已验证任务。

## 阶段报告与完成

每完成一个 Phase，在 `commentary` 报告已勾选任务、验证命令及结果、剩余任务和下一个任务 ID，然后立即继续。不得把阶段报告作为最终回复。

仅在以下条件之一满足时才能发送最终回复：Feature 全部完成并已验收；触发软门禁且需要用户决策；用户明确要求暂停或仅要状态。优先在同一活动回合循环执行“选择下一任务 → 实现 → 验证 → 勾选 → commentary 进度”；若 Goal 运行时切分 turn，则依靠 Goal continuation 从持久化任务状态恢复。不得在 Phase 检查点主动结束 Goal。
